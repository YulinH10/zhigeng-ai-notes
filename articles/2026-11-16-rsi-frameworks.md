# 深度解析 RSI 技术及四大前沿框架实践

学习日期：2026-11-16 · 分类：AI Agent

上一篇写到让 Agent 自己修 bad case：发现问题、提出修改、跑评测，再把可复核的结果交回来。继续往前走，就会遇到一个更难的问题：Agent 能不能从修复经历中改变自己，让下一轮不仅做得更好，也更懂得怎样改进？

这正是递归自改进（Recursive Self-Improvement，RSI）值得研究的地方。它已经出现了具体的系统实现，也最容易被“自动改 Prompt”“自己写代码”“通向超级智能”几种叙事混在一起。

本文围绕 Harness²、Evo²、RRSI、OO-Harness，拆解改进对象、反馈来源、跨轮继承和部署边界。框架机制依据原论文及作者仓库整理；后文的 Query 理解案例、实验设计和接入方案是工程建议，未在本文中执行框架复现。资料核对截至 2026 年 11 月 16 日。这里的 Evo² 指权重与 Harness 协同进化研究。

## 先说清楚：RSI、AGI 和 ASI 在讨论什么

RSI 讨论的是**系统怎样改进自己，以及改进成果怎样继续影响后续改进**。AGI 讨论跨任务的通用能力，ASI 讨论在广泛认知任务上超越人类的能力水平。三者分别关注改进机制与能力范围、程度，不能排成一条必然实现的升级路线。AGI 的具体判据仍有不同口径，本文采用能力广度与表现深度这两个维度理解它。[能力分级参考：Levels of AGI](https://arxiv.org/abs/2311.02462)

一个只会优化代码修复流程的系统，也可以研究递归自改进；一个能力很强的模型，也可能没有任何持久更新自己的机制。即使一套系统能反复提高分数，也不能据此推出它会无限加速，或者已经获得通用智能。

在当前 Harness 研究中，RSI 的用法有宽有窄。有的工作把“反复修改自己的持久组件”称为系统级 RSI；更严格的口径还要求修改产生、评价或保留后续改进的机制。阅读时需要交代采用哪种口径，不能只看名字里有没有 recursive。[定义与证据层次参考：Trustworthy RSI 综述](https://arxiv.org/abs/2610.35193)

### 用两份状态看清“递归”

为了分析工程系统，可以把任务执行和改进过程分开表示。下面是本文的简化记号，不是某篇论文的原公式：

```text
执行系统 A_t = 模型 M_t + Harness H_t
改进机制 U_t = 提案策略 + 经验 + 搜索流程

任务执行 → 轨迹与反馈 E_t
U_t(A_t, E_t) → 候选执行系统
外部验收 → 保留 A_(t+1)
从改进经历中学习 → 形成 U_(t+1)
下一轮实际使用 A_(t+1) 与 U_(t+1)
```

H 是执行任务的脚手架，包括 Prompt、工具接口、上下文管理、技能、记忆和控制流。U 是负责改进它的机制。H 变了，说明任务 Agent 被优化了；U 也通过经验或训练发生持久变化，并在后续轮次使用，才更接近“改进如何改进”。

### 怎样判断一个系统到底做到了哪一步

我会依次检查五件事：

1. **修改有没有留下来？** 同一道题多想几次、重新采样或重试，不足以说明发生了持久自改进。
2. **后继系统有没有真正接棒？** 必须记录下一轮加载的 Prompt、代码、经验库或权重版本，不能只产出一份建议书。
3. **改进机制有没有变化？** 若只是固定优化器反复搜索，应标为自动优化；若经验影响后续提案，或改进者被训练，应具体说明变化发生在哪里。
4. **进步是否超出已见任务？** 用独立任务和旧能力回归检查收益，排除记答案、误差波动与增加推理预算的影响。
5. **变化后的改进者是否更有效？** 从相同起点出发，在相同总预算下比较冻结 U 与更新 U，观察后续搜索收益，而不只比较最终某个 H 的分数。

这是一套预研判据。日志里出现几十轮循环，只证明循环执行过。要声称“递归机制带来了进步”，还需要让后继版本、独立评测和对照实验把因果关系补齐。

## 技术路径：改什么，取决于反馈能不能跟上

工程上可以先按变化对象区分三条路径。

**执行 Harness 自进化。** 基础模型保持固定，修改提示词、工具说明、上下文压缩、错误恢复和控制逻辑。它适合只有模型 API 的团队；困难集中在代码可执行、收益归因和跨任务泛化。

**改进经验持续积累。** 把成功机制、失败原因和适用条件写入可复用经验，供后续提案使用。经验不是越多越好：过时记录、相互矛盾的规则和任务答案都可能污染后继版本，需要检索、淘汰与来源管理。

**改进者权重与 Harness 协同更新。** 将修改轨迹及其效果转成训练信号，训练负责提出和反思修改的模型。门槛上升到训练数据质量、训练资源、奖励设计和模型版本回滚；训练了改进者，也不等于执行模型被训练。

真正难的通常不是让 LLM 生成一个 diff，而是让“产生修改—执行修改—独立验证—保留有效变化”可靠运转。最低技术条件包括：版本化修改对象，可重置的运行环境，可核验的反馈，独立验收，以及覆盖探索和验证的总预算。缺少其中一环，自进化很容易停留在生成建议，或把偶然成功固化进系统。

## 四个框架，各自解决哪一个瓶颈

![图 02：四大框架的改进对象、反馈方式与跨轮继承对照](https://yulinh10.github.io/zhigeng-ai-notes/assets/articles/rsi/framework-comparison.svg)

### Harness²：没有标准答案，怎样指导在线改动

Harness² 面向新任务到来时缺少标准答案的场景。任务内采用 **Propose–Probe–Compose**：先取得基线执行记录，分别提出通用机制与领域机制候选；在相同任务、匹配环境下试跑；根据轨迹差异选择、修改或合并有证据支持的变化，再执行合成后的版本。它支持并行探索和顺序深化。

任务结束后，系统把采用过的 Harness 与改进经验存入库，帮助后续任务。新任务从共同的基础 Harness 出发，由经验指导选择性复用。这里持续变化的是经验库，模型权重、阶段指令和决策规则保持固定。**执行对照提供行为证据，并不构成正确性证明。**[机制来源：Harness² 论文第 2 节](https://arxiv.org/html/2610.14224v1)

作者实现将系统提示词、护栏、记忆、工具指引、子 Agent、技能、脚本和插件暴露为八类可编辑组件，提供本地 demo，以及 OpenCode、Codex 执行器接入。真正跑模型基准还需要相应环境和凭据；demo 跑通不代表业务收益已验证。[实现入口：Harness² 作者仓库](https://github.com/google-research/harness2)

**放到内部 Agent 怎么试？** 假设一个资料整理 Agent 经常漏掉最终文件校验。可以提出两个候选：一个加入通用的产物检查，另一个加入文档领域的版式检查。用可重置环境重放同一个任务，比较它们是否真的发现缺页、坏链接或空文件，再决定保留哪些机制。

在线探测应先落在只读任务或隔离副本。重复执行一次真实业务写入，可能重复发通知、建工单或修改数据。接入前需要处理幂等和环境重置，不能把重复试跑默认视为无副作用。

我会优先借鉴它的“保留有证据的适用经验”。若总结只写“以后认真检查”，它对下一轮几乎没有约束力；若写清触发条件、具体检查项和失败证据，后续提案才有可以利用的材料。

### Evo²：让负责改进的模型也学会进步

Evo² 用共享参数的一套策略承担 Proposer 与 Reflector 两种角色：前者编辑 Harness，后者读取 diff、性能变化与执行轨迹，决定修订、引入其他分支的策略，或者保留候选。候选形成搜索树，跨分支的机制通过 crossover 适配后还要重新评测。

其 EvoTIDE 管线通过编辑提取与前缀续写恢复可用轨迹，先做监督微调（SFT），再交错进行两种角色的组相对策略优化（GRPO）。更新后的改进者继续参与搜索；**任务执行模型在协同进化期间保持固定**。因此，它比固定改进者的搜索更直接地触及 U 的变化。[机制来源：Evo² 论文第 3 节](https://arxiv.org/html/2610.13025v1)

**放到内部 Agent 怎么试？** 在 Query 理解任务里，Proposer 可能修正一个“品牌加品类”的解析流程，Reflector 根据新旧输出判断它是否误伤了地点词。每次尝试都保留父版本、修改、失败原因和执行结果；将来有足够可靠轨迹时，再研究训练改进者。

只让两个角色互相评论，没有轨迹训练和后继模型复用，属于借鉴其双角色搜索。只有封闭 API、无法训练改进者时，应先评估这部分收益。单独接上反思 Prompt，不能声称复现了完整的权重与 Harness 协同进化。

这里还有一个实际门槛：反思写得通顺，不意味着它值得训练。训练目标应关联被执行和验证的改动效果，否则模型可能学到的是更会解释成功，而不是更会提出有效修改。检验时还要把训练成本算进去。

### RRSI：怎样避免越改越像“背题”

RRSI 针对有限进化任务被反复使用造成的过拟合，正则化提案与选择过程。提案端逐步收紧原子修改数量，保留正负历史，并在停滞时探索未充分尝试的组件；选择端筛查任务泄漏，以噪声容忍和成本规则约束晋升，并提出删除长期无贡献组件的目标。

它把修改稀疏性、结构剪枝和复杂度控制分别类比为 L0、L1、L2 正则化，**这些是离散搜索层面的类比，不是在给基础模型权重加同名损失**。噪声带也是经验性控制，不能据此声称任意多轮搜索都有统计保证。[机制来源：RRSI 论文第 3 节](https://arxiv.org/html/2609.24972v2)

作者实现把候选放入独立 Git worktree，记录每次修改的组件、假设、分数与成本变化。代码将泄漏筛查、预算调度、选择规则和领域验收分开实现，适合作为内部离线优化器的参考。模型侧的 critic 需要与外部硬约束配合，不能单独充当权限边界。[实现入口：RRSI 作者仓库](https://github.com/google-research/rrsi)

**放到内部 Agent 怎么试？** 某轮发现“商场加品牌”识别错误，候选直接把那家商场与品牌写进 Prompt，眼前分数很容易提高。更有复用价值的候选应提出可检验的一般机制，例如调整地点修饰与品牌实体的判定顺序，再用未见实体组合检查它。

这个区别决定了历史记录应该怎么写。只记“加一条规则后涨分”，下一轮仍会继续加规则；记下假设、适用范围、失败反例和成本，才有机会否定一种方向，或者删掉一条已无贡献的机制。

RRSI 的工程价值也在这里：允许保持当前版本，允许删减，允许承认这轮没有足够证据。自进化流程不应该要求每轮都交出一个新冠军。

### OO-Harness：不同任务需要不同执行策略

OO-Harness 将一个全局 Harness 扩展成可继承的类层次。发现阶段，演化 Agent 从执行记录中组织任务簇，选择父类，创建覆盖或新增方法的子类，在目标簇上评测，并积累设计经验与路由经验。

测试时，类层次与经验保持冻结。路由器依据任务、可观察的基础执行轨迹、类说明和经验，选择专用类，或者复用基础结果。继承的方法在同一个实例内执行，祖先不是逐层运行的独立 Agent；测试评分与隐藏答案也不提供给路由器。[机制来源：OO-Harness 论文第 3 节](https://arxiv.org/html/2610.28380v1)

**放到内部 Agent 怎么试？** Query 理解可能有快速词法判断、实体消歧、复杂组合解析等执行需求。一个总 Prompt 同时承担全部流程，可能既拖慢简单输入，又漏掉复杂输入的证据要求。可以保留一个基础实现，再探索少量带明确适用条件的专用实现。

需要同时衡量两种收益：专用实现选对时有多好，以及真实路由会不会选错。只报告“给每道题选最好的类”的理想结果，会隐藏路由损失。沿用论文的基础轨迹路由方式时，还要计算这次基础执行的成本。

类继承本身也不是安全隔离：子类覆盖方法可能绕过父类检查。若鉴权、预算与发布控制必须对所有变体生效，就应放在继承体系外的宿主执行层。

## 选型时，先找到业务的主要瓶颈

这四项工作优化的对象和实验条件不同，论文分数不能直接拼成框架排名。对内部预研，我会这样确定第一步：

- **有稳定任务和可靠评分，担心反复优化过拟合：** 先借鉴 RRSI，做预算、历史、泄漏筛查与保守晋升。
- **新任务多，在线缺少答案，但能够安全重放：** 试 Harness² 的执行对照与经验复用，并独立验收交付物。
- **任务类型差异大，统一策略经常互相牵制：** 试 OO-Harness 的少量专用实现与路由，单独评测误路由和额外延迟。
- **已有大量可核验修改轨迹，并具备模型训练能力：** 再研究 Evo²，检验训练改进者能否提高后续搜索效率。

这是基于机制的工程选型建议。Harness² 与 RRSI 有本文核对过的作者代码仓库；Evo² 与 OO-Harness 在本文中按论文设计分析，不将第三方教学代码视为作者实现，也不假定四者都是可直接替换的生产 SDK。

几种思路可以组合，但首次实验最好只引入一个主要变量。否则最后涨分了，很难判断究竟来自经验、搜索次数、专用策略还是更高的模型调用预算。

## 一个可落地的 Query 理解预研方案

下面设计一个有限范围的离线实验：冻结基础模型、标签标准和评测程序，让 Agent 优化精泛品识别的一份 Prompt。目标是验证闭环是否有效，以及复杂机制是否值得增加。

### 先把数据和预算安排好

**进化集**提供样本、标签、预测和错误分析，用于提出修改。**选优验证集**只经独立评分服务返回受限汇总结果；它被反复用于选版本后，也会产生自适应过拟合。**封存测试集**用于阶段验收；一旦结果用于指导修改，就应按已使用数据管理，不能继续称为未见测试。

实体、模板、来源和时间上的近重复要跨集合排查。另留一组分布外数据，检查新行业、新实体或输入变化。更换模型、评分规则或环境时，重跑同一窗口下的基线，避免把环境漂移算成优化收益。

总预算包括提案、反思、候选执行、筛查、验证、记忆整理和最终执行。评测预算对齐后，比较三组：固定 Prompt 的直接执行、简单失败经验摘要、带约束的 Harness 优化。若研究递归机制，再增加“冻结改进经验”和“持续更新经验”的对照。

### 让每次修改带着一个能被否定的假设

例如：“品牌词被地点规则提前截断，因此调整两者的判定顺序。”围绕这一假设提交小范围 diff，说明可能改善的样本，也说明可能误伤的样本。

结果包至少包含父版本、候选版本、修改假设、实际 diff、数据与评分版本、各类指标、总成本、失败样本，以及接受或拒绝的原因。保留拒绝记录，避免后续反复探索已经失败的同一种改动。

下面的流程是工程示意，晋升阈值需要按实际样本量、误差与业务目标事先设定：

```text
冻结评分器、测试数据、权限策略与总预算
重复运行当前版本，估计基线波动
在隔离副本中提出一个有明确假设的小改动
先检查修改范围、任务泄漏和可执行性
再评测进化收益、验证回归和资源消耗
证据不足：保留当前版本，记录原因
达到预设标准：登记候选，提交人工验收
批准后：按不可变版本激活，保留旧版与回滚入口
```

### 验收时看什么

质量至少看总体指标、关键类别指标和旧能力回归，避免多数类提高掩盖少数类退化。成本看全链路 token、调用次数、端到端延迟及后续复用次数。稳定性看重复运行的分布和失败类型，不能只保存最好的一次。

如果声称“改进者更会改了”，应从同一个执行 Harness、匹配的任务和总预算出发，比较更新前后的改进机制，记录其后续增益与无效尝试。一次最终分数的比较，无法独立回答这个问题。

先让这份实验交出完整证据。若简单经验摘要已经够用，就没有必要为了增加递归层数而扩大系统。

## 安全边界要落在候选改不动的地方

自进化的风险可以很具体：记住评测答案、删除失败日志、污染共享记忆、通过工具输出注入恶意指令，或者把审批检查视为影响通过率的障碍。研究综述也指出，修改一旦进入后继系统，可能继承原有缺陷，并削弱先前验证与监督的有效性。[风险依据：Trustworthy RSI](https://arxiv.org/abs/2610.35193)

落地时应先划清允许编辑的区域。Prompt、工具描述、实验技能和候选控制流可以在隔离环境探索；测试答案、评分器、身份凭据、访问控制、审计和部署授权应由独立执行层控制。模型对自己的承诺，不能替代文件权限、接口权限与运行时限制。

### 哪些步骤可以自动推进

在事先批准的范围内，样本归类、失败分析、小范围候选编辑、隔离试跑、统计、拒绝明显无效候选和生成结果包，可以自动完成。每次调用仍受工具白名单、读写范围、时间和预算上限控制。网页、工具结果与历史记忆都作为输入数据处理，不能给自己授予权限。

### 哪些变化必须保留人工审核

对上述内部预研，我会将以下动作设为人工审核节点：

- **改变目标或验收口径：** 修改标签定义、评分程序、金标或安全阈值，必须重新登记基线，不能与旧分数直接续接。
- **扩大权限或外部影响：** 增加可写数据源、执行权限、网络范围、依赖插件，或接入真实通知与业务写入。
- **持久化跨任务行为：** 合入共享规则、共享记忆、通用脚本，或激活训练后的改进者；需要审查来源、范围、冲突与敏感信息。
- **修改改进机制或保护机制：** 搜索策略、候选晋升、剪枝、审批、审计、回滚发生变化时，单独评测其对后继版本的影响。
- **部署生产版本：** 基于已冻结的候选、回归证据和回滚方案审批，再做有限范围激活和运行观察。

这是本文给出的部署策略，具体阈值和授权范围应在启动前确定。人需要审的是具体改动与影响证据，不能只收到“分数提高，请批准”这一句话。

### “正则约束”和“正则表达式”分别能做什么

RSI 中的正则化，主要指限制改动容量、控制复杂度、约束成本和剪掉无效机制。正则表达式可以帮助筛查题号、数据集标识或已知答案片段，但它只是泄漏检测的一层，容易漏掉改写、编码与语义等价内容。

更可靠的组合是：小范围修改、结构化 diff、来源审查、独立评测、可执行的硬边界和人工抽检。预算耗尽、连续失败或保护规则被触碰时，由外部监督器停止新一轮探索；停止机制和版本指针都应置于候选写权限之外。

## 当前能力上限：收益、成本和长期递归仍要分别证明

这四项研究提供了可操作的机制，但本文核对的实验不足以证明无限期稳定的自我加速、任意任务上的持续增益，或可以取消人的监督。短期任务成绩、后继版本表现，以及改进机制本身变强，需要分别取证。

成本也会改变判断。2026 年 11 月的《The RSI Tax》在其持续任务流实验中发现，简单的有限笔记基线可以匹配或超过被比较的部分 RSI 方法，同时节省大量总 token。这个结论有特定模型、任务流和预算范围，不能据此否定所有 RSI，但足以要求预研加入简单基线，并统计改进过程的开销。[成本研究：The RSI Tax](https://arxiv.org/abs/2611.13524)

对内部 Agent，我会先回答一个具体问题：在固定预算和外部验收下，这套系统能否持续交回比当前版本更好的候选，并清楚说明哪些修改没有奏效？等独立任务上的收益、旧能力保留和总成本都有证据，再逐步开放更多可进化组件。

建议先读各论文的方法章节，画出“改什么、谁评分、留下什么”，再检查实现与实验设置。本文两张图为机制示意，Query 理解方案为预研设计，均不表示作者已在该业务上获得验证。

1. [Levels of AGI for Operationalizing Progress on the Path to AGI](https://arxiv.org/abs/2311.02462)：能力广度、深度与自主性的区分。
2. [Harness²: Recursive Agent Harnessing for an Open World，v1](https://arxiv.org/html/2610.14224v1)：任务内执行对照、跨任务经验库；[作者仓库](https://github.com/google-research/harness2)。

5. [Object-Oriented Harness: Evolving Agent Harnesses through Object-Oriented Design，v1](https://arxiv.org/html/2610.28380v1)：类继承、任务专用化与冻结路由经验。
6. [Trustworthy Recursive Self-Improvement in the Era of Large Models](https://arxiv.org/abs/2610.35193)：改进有效性、约束保留与监督的证据要求。
