# 让 Agent 自己修 bad case

学习日期：2026-10-22 · 分类：AI Agent

给 Agent 一批 bad case，让它分析原因、改 Prompt、部署、跑评测，直到拿出一个更好的版本。这件事听起来已经很完整了。可等这一批做完，还是得有人找下一批问题，判断该交给谁，再追着问结果。

## 先让一轮迭代跑完

起点很朴素：人把问题和验收标准交代清楚，中间的分析、修改、部署、评测交给 Agent。没有达标就继续，达标后再交给人复核上线。

![图 01：从定义问题到人工验收的一轮自主迭代](https://yulinh10.github.io/zhigeng-ai-notes/assets/articles/harness/redraw-01.svg)

这条线里，每个箭头都得能真的执行。网页上有一个部署按钮，不等于 Agent 会部署；人能在页面里读懂一张评测表，也不等于 Agent 能取到结构化结果。

所以第一步要接通的是四件很日常的事：改代码或 Prompt、部署、发起评测、下载结果。代码库、分支、环境、权限、评测范围也要一起固定下来，否则跑完几轮，很容易连“这次测的到底是哪一版”都说不清。

![图 02：研发工具和运行环境需要一起交给 Agent](https://yulinh10.github.io/zhigeng-ai-notes/assets/articles/harness/redraw-02.svg)

跑得久以后，又会冒出另一组问题。它可能做完一步就停下来等人，也可能对着同一个报错反复重试；分析积累得太多，上下文先用完了。

这里的处理办法挺实用：一次只推进一件事；同样的异常再次出现，先查原因；复杂分析交给子 Agent，主 Agent 只留轮次、当前版本、任务和必要的结果。交接时不复制整段聊天记录。至于什么时候该停，要事先写清楚——完成了、预算用完了、缺权限了，或遇到了需要人决定的边界，都有各自的出口。

![图 03：长任务的执行约束，以及父子 Agent 之间的上下文交接](https://yulinh10.github.io/zhigeng-ai-notes/assets/articles/harness/redraw-03.svg)

## 分数涨了，也要看看它改了什么

有个细节很容易忽略：优化者看到“某个百分比没有来源”被扣分，就把那个数字写进 Prompt，要求以后别编这个数字。眼前这道题可能好了，换个数字还是同一个问题。

这时要把用于分析的样本和用于选版本的验证集分开。前者给问题、回答、评分和理由；后者只给汇总分数。每轮从当前擂主出发，挑战者通过验证才替换它。这里说的“训练集”用于改 Prompt，没有更新模型权重。

![图 04：优化样本与验证集分开，挑战者通过后才替换擂主](https://yulinh10.github.io/zhigeng-ai-notes/assets/articles/harness/redraw-04.svg)

另一个有意思的记录，是 Agent 会主动删规则。一个角色约束太强的 Prompt，把本来可以正常回答的闲聊也挡住了。开始时它加任务路由、加完整性要求；继续看结果，又把其中一些要求拿掉。

下面四轮里，第二、三轮的优化样本分数都比第一轮高，验证集却掉了，擂主没有更换。第四轮做了减法，验证集到了 0.7811，才晋升为新擂主。这个过程比“每轮继续补一条规则”更值得记下来。

![图 05：四轮迭代中，验证集决定是否晋升；规则也可以删除](https://yulinh10.github.io/zhigeng-ai-notes/assets/articles/harness/redraw-05.svg)

这一阶段有一份 17 小时、16 轮的运行记录，最后产出了一个经人工复核后上线的候选。五个维度里，安全性持平，其余四项小幅上涨。

![图 06：一次 17 小时、16 轮运行的五维评测记录](https://yulinh10.github.io/zhigeng-ai-notes/assets/articles/harness/redraw-06.svg)

这些数字来自同一次实践记录，后面出现的入池数量、回测数量和覆盖率也各有统计范围。对我来说，它们的用处是把流程讲具体。验证分数被反复用于选优，仍然需要另外保留最终测试，不能因为题目藏起来了就当作不会过拟合。

## 这一批修完，下一批谁来派

到这里，Agent 已经能自己修一批问题了。可把完整链路摊开，发现、初步归因、派工、收结果，还都在人手里。中间两步自动了，人仍得围着它转。

![图 07：修复和验证已经自动化，前后的发现、派工和回收仍由人推动](https://yulinh10.github.io/zhigeng-ai-notes/assets/articles/harness/redraw-07.svg)

Loop 接的是这段工作。外循环找问题、分派任务、收回结果，决定关闭、保留待判定，还是改派；内循环接到一个任务，完成诊断、方案、审查、实施和验证，再把证据交回去。

两边交接的是任务包和结果包。任务包里有样本、初步归因、范围和验收要求；结果包里有版本、输出、判定和下一步建议。Harness 则铺在两个循环下面，提供工具、状态、执行约束和评测。

![图 08：通过任务包和结果包连接内外循环，共用一套 Harness](https://yulinh10.github.io/zhigeng-ai-notes/assets/articles/harness/redraw-08.svg)

这套流程把外循环分成入池、调度、通知三个角色；修复小队有队长、方案设计者、审查者、实施者和验证者。八个角色看着不少，每个角色负责的事都很具体。

![图 09：全局控制小队与修复小队的八个角色](https://yulinh10.github.io/zhigeng-ai-notes/assets/articles/harness/redraw-09.svg)

我更关心这里的交接边界：调度器不替下游诊断，实施者不替自己判定成功，验证者要拿实际输出说话。角色是否需要拆成八个，可以按任务复杂度再定。

## 先把混在一起的问题拆开

入口收到的是一堆混杂的 bad case，直接派工会造成重复修复，也会把不同原因塞进同一张单。

入池先做拉取、归一化、去重、聚类。一份记录里，404 个候选跨工单去掉 81 个重复，剩下 323 个，再整理成 16 个可路由的问题组。

![图 10：404 个候选经去重和聚类，形成 16 个路由组](https://yulinh10.github.io/zhigeng-ai-notes/assets/articles/harness/redraw-10.svg)

调度器拿到这些组后，按规则建单、派单、处理回传；碰到边界问题，再交给人。它往下传编号、标签、样本和期望产出，把诊断留给修复小队。

通知也单独留一个角色：把需要人判断的材料送到，拿到回复后写回原工单。送达是一回事，作出判断是另一回事。

![图 11：调度负责派单与回流，通知负责送达并记录回复](https://yulinh10.github.io/zhigeng-ai-notes/assets/articles/harness/redraw-11.svg)

再往下看一张“没有澄清”的工单，里面有 25 条样本。这个标签很像一个确定的问题，拆开才发现至少有三类：输入太短，确实不该直接答；多义词被模型擅自补全；以及本来就清楚，只是被贴错了标签。

![图 12：同一个“没有澄清”标签下，混着三类不同问题](https://yulinh10.github.io/zhigeng-ai-notes/assets/articles/harness/redraw-12.svg)

所以，初步归因只能帮助路由。到了修复环节，还得拿样本重新查一遍。

## 证据够了，再动 Prompt

这一组问题先查了路由、工具和检索结果，才把范围缩到回答策略上。剩下那个最关键的问题，仍然得由人来定：短输入经过检索，虽然找到了一个合理解释，但用户并没有确认，要不要先澄清？

方向确认后，方案才进入审查。改什么、不改什么，怎么回滚，拿哪些例子回归，出现什么结果就否决，都在实施之前写下来。

![图 13：从诊断证据到人工确认，再通过方案审查进入实施](https://yulinh10.github.io/zhigeng-ai-notes/assets/articles/harness/redraw-13.svg)

这次落到文件里的改动很小：一份 Prompt，两处规则。先给原来的“直接回答”补一个例外，再把例外写成可执行的判断。多义又不明确的输入，先确认它在问什么；短语、语音碎片或者错字，先问一个最关键的问题，不把缺失的历史补出来。

![图 14：一份 Prompt 的两处改动，从规则例外到可执行的澄清动作](https://yulinh10.github.io/zhigeng-ai-notes/assets/articles/harness/redraw-14.svg)

“需要澄清”这四个字太宽。写成“什么情况下，先问哪一个问题”，才方便实施，也方便回测。

## 回测之后，工单要有去向

验证从版本确认开始：部署的是不是这次提交，评测打的是不是这个环境。接着做目标回测，再跑基准回归，最后过质量门槛。

前面的 25 条样本里，3 条先改派；余下 22 条各请求 3 次，一共 66 次。最后按样本判定：20 条通过，1 条失败，1 条待定，加上前面的 3 条改派。这里的 20 是样本数，66 是请求数，不能混着算。

![图 15：66 次请求对应 22 条样本，最终回收为通过、失败、待定和改派](https://yulinh10.github.io/zhigeng-ai-notes/assets/articles/harness/redraw-15.svg)

失败的那条很能说明问题。模型答错了某家医院的等级，于是 Prompt 被补上“按工具结果作答，并说明来源”。改动生效后，同一个问题测了三次，还是全错。

往上查才发现，数据库把“三级专科”标成了“三甲”。模型已经在遵守新规则，只是它拿到的数据就是错的。

![图 16：Prompt 约束已经生效，错误仍来自上游数据](https://yulinh10.github.io/zhigeng-ai-notes/assets/articles/harness/redraw-16.svg)

这时继续改 Prompt，反而容易把一个数据问题绕成更多例外。修复小队应该把版本、回测输出和数据证据交回调度器，经确认后改派给检索或数据小队。谁负责重新路由，也要写在流程里，免得几个 Agent 各自做决定。

![图 17：修复失败带着证据回到外循环，再改派给数据小队](https://yulinh10.github.io/zhigeng-ai-notes/assets/articles/harness/redraw-17.svg)

这也是我觉得 Loop 最有用的地方。一次修复没成功，后面的工作仍有人接；待定的工单留着原因，改派的工单带着证据。否则，“本次无法修复”很容易成为整件事的终点。

## 人从哪里退出来，又留在哪里

把前后两段连起来，Harness 管一轮任务怎样执行、怎样验证；Loop 管下一轮从哪里来，以及结果到哪里去。分角色协作，让实施和判定各自有负责人。

那份记录里，约 20% 的 bad case 已经由这条链路处理。比起单看这个比例，我会更想持续记录：哪些类型能关闭，哪些总在改派，哪些需要人反复确认。这些地方会告诉我们下一步该补评测、改数据，还是重新划任务边界。

![图 18：Harness、Loop 和角色分工各自承担的部分，以及阶段性覆盖范围](https://yulinh10.github.io/zhigeng-ai-notes/assets/articles/harness/redraw-18.svg)

人也没有从流程里消失。以前要逐步推动发现、归因、分派和回收，现在更多是在外面定边界、抽样看、审计和担责。权限怎么给，哪些情况必须停下来，发布谁来批，出了问题谁来回滚，仍然需要明确的人。

![图 19：从逐个推动节点，到在循环外定边界、抽样、审计和担责](https://yulinh10.github.io/zhigeng-ai-notes/assets/articles/harness/redraw-19.svg)

## 放到自己的任务里

如果拿 Query 理解来试，我会先挑一类能稳定复现的错误，比如精泛品识别里一组容易混淆的输入。把标签标准和通过条件写清楚，接通批量推理、评分、错误导出，再让 Agent 只改一份 Prompt。

第一轮先看它能不能把版本、目标回测、回归结果和失败样本完整交回来。等这件事稳定了，再接定时拉取、去重、派单和结果回收。没必要一开始就把所有角色都配齐。

![图 20：从自动评测起步，跑通小闭环后再接持续调度](https://yulinh10.github.io/zhigeng-ai-notes/assets/articles/harness/redraw-20.svg)

我想先做的就是这一步：找一组老是要手动重跑的样本，让 Agent 从改动一直做到交回可复核的结果。先看看，自己究竟还得在哪些地方伸手。
